# Coding Style

## イミュータブル（最重要）

既存のオブジェクトを変更せず、常に新しいオブジェクトを作る。

```
NG: modify(original, field, value) → original をその場で書き換える
OK: update(original, field, value) → 変更を含む新しいコピーを返す
```

理由: 隠れた副作用を防ぎ、デバッグを容易にし、並行処理を安全にする。

## ファイル構成

多数の小さいファイル > 少数の大きいファイル。

- 高凝集・低結合
- 1ファイル 200〜400 行が目安、800 行を上限
- 大きくなったモジュールからユーティリティを切り出す
- 種類（controllers/, utils/）ではなく機能/ドメイン単位で整理する

## TypeScript（採用した場合）

- `any` 禁止。`interface` / `type` を定義する
- 外部データ（API レスポンス、ファイル、ユーザー入力）は `unknown` で受けてスキーマ検証してから型付けする
- `as` キャストは境界の検証直後のみ

## エラー処理

- すべての層で明示的に扱う。黙って握りつぶさない（空 catch 禁止）
- UI 向けには人間が読めるメッセージ、サーバー側には文脈付きの詳細ログ
- 失敗しうる処理の戻り値は成功/失敗を型で表現する（例外を投げ続けない）

## 入力検証

システム境界では必ず検証する。

- ユーザー入力は処理前に検証
- スキーマベースの検証ライブラリがあれば使う
- 早く失敗し、明確なエラーメッセージを出す
- 外部データ（API、ファイル、環境変数）を信用しない

## 完了前チェックリスト

- [ ] 名前が読みやすく、意図を表している
- [ ] 関数は小さい（50 行未満）
- [ ] ファイルは焦点が絞られている（800 行未満）
- [ ] ネストが深くない（4 段以下）
- [ ] エラー処理が適切
- [ ] ハードコードした値がない（定数か設定に出す）
- [ ] ミューテーションがない
