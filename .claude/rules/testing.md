# Testing

## カバレッジ目標: 80% 以上

必要なテストの種類:

1. **Unit** — 個々の関数、ユーティリティ、コンポーネント
2. **Integration** — API エンドポイント、データベース操作、外部サービスとの境界
3. **E2E** — 重要なユーザーフロー（フレームワークはスタック決定後に選ぶ）

## TDD（必須ワークフロー）

1. テストを先に書く（RED）
2. 実行して**失敗することを確認**する
3. 最小限の実装を書く（GREEN）
4. 実行して通ることを確認する
5. リファクタリング（IMPROVE）
6. カバレッジを確認する（80%+）

バグ修正は Prove-It パターン: バグを再現するテストを書き、失敗を確認してから直す。

## ハーネス内での役割分担

- **tester** がテストを書く・実行する。受入基準（spec.md の `verify:`）が通ることも tester が確認する
- **builder** はテストを書き換えて通すことを**禁止**。実装を直す
- テストが間違っていると builder が判断した場合は、reviewer への報告に理由を書く（勝手に変えない）

## テストが失敗したとき

1. まずテストの分離を疑う（順序依存、共有状態、時刻依存）
2. モックが正しいか確認する
3. 実装を直す。テストを直すのはテストが間違っている場合のみ
4. 根本原因が分からないまま再試行しない

## 書き方

- テスト名は「何をしたら何が起きるべきか」を表す
- 1テスト1アサーション群（複数の無関係な検証を混ぜない）
- 外部サービスはモックする。時刻・乱数は注入する
- フレーキーなテストは skip せず直す
