# /intent — 意図の定義（人間介入ポイント 1/3）

`$ARGUMENTS` を feature 名（kebab-case）として扱う。未指定ならユーザーに1行で聞く。

## 目的

コードを書く前に「何を・なぜ」を人間の言葉で固める。ここでは設計や技術選定に踏み込まない（それは `/spec` の仕事）。

## 手順

1. `specs/<feature>/intent.md` が既に存在するか確認する。
   - 存在して承認済み（`approved_by:` が埋まっている）なら「承認済み。`/spec <feature>` に進めます」と伝えて終了。
   - 存在して未承認なら、その内容を読み込んで討論の続きから再開する。
2. `intent-writer` サブエージェント（model: fable）に委譲する。渡すもの:
   - feature 名
   - ユーザーの最初の発言（そのまま）
   - テンプレート `specs/_template/intent.md` のパス
   - 既存 intent.md があればそのパス
3. intent-writer はユーザーと討論し、次を引き出してから `specs/<feature>/intent.md` を書く:
   - 問題（今なにが困っているか）
   - 望む結果（できあがったとき何が変わるか）
   - 影響範囲（触るシステム・データ・ユーザー）
   - 制約（やらないこと・守ること）
   - 未解決の問い
4. 書き上がったら、ファイルの全文ではなく **要点を5行以内** でユーザーに提示し、承認を求める。
5. 承認は人間が承認欄に記入して commit することで成立する。次の文言を提示する:

   ```
   承認するなら intent.md 末尾の承認欄を埋めてください:
     approved_by: <あなたの名前>
     approved_at: YYYY-MM-DD
   修正したい点があればそのまま伝えてください。
   ```

6. 修正要望があれば intent-writer に差し戻して更新する。承認されるまで `/spec` に進まない。

## 禁止事項

- 技術スタック・ファイル構成・API 設計をここで決めない（未解決の問いとして書き残すのは可）。
- ユーザーの承認なしに承認欄を埋めない。
- コードを書かない。
