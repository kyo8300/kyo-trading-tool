# kyo-trading-tool 勉強会スライド用まとめ

> 発表者向けのメモ。各セクションがそのままスライド 1〜2 枚分になる想定。
> API キー・口座情報・残高・実際の損益は一切含めていない（売買ルールの「比率」と設計上の数字のみ）。

---

## 1. アプリの概要

**AI が SNS 発信者の銘柄言及データを読み、人間が決めた売買ルールの範囲内で米国株を自動売買する個人用ツール。**
全ての判断・注文・約定・損益を SQLite に記録し、「何を根拠に買い、なぜ売り、どうなったか」を後から数字で検証できる。

一言で: 「AI が銘柄を選び、ルールが財布の紐を握り、記録が答え合わせをする」

## 2. 全体アーキテクチャ

### 構成要素（レイヤー）

| レイヤー | 役割 | 主なモジュール |
|---|---|---|
| sources | 集約データ（ツイートアーカイブ）の取り込みとスキーマ検証。銘柄ごとの「言及履歴 + 抜粋」= evidence を導出 | `sources/serenity/`, `sources/evidence.py` |
| market | 株価・出来高・市場カレンダー取得（Alpaca Market Data） | `market/alpaca_data.py`, `fake_data.py` |
| analysis | LLM に evidence + 株価 + ルール要約を渡し、構造化 JSON（buy / hold / skip + 根拠 + 確信度）を受け取る | `analysis/prompt.py`, `llm_client.py`, `output_schema.py` |
| rules | 人間が書いた YAML の売買ルール。買い前チェック、保有中の売り判定、損失上限 | `rules/entry_checks.py`, `exit_checks.py`, `loss_limits.py`, `lock.py` |
| engine | 1 サイクルのオーケストレーション。承認 → 発注 → 約定ポーリング → キルスイッチ | `engine/cycle.py`, `approval.py`, `order_executor.py`, `kill_switch.py` |
| broker | 証券会社 API の抽象化（Protocol）。Alpaca 実装 + テスト用 Fake | `broker/alpaca_broker.py`, `fake_broker.py` |
| ledger | SQLite への記録（12 テーブル）。約定からポジション・トレードを導出 | `ledger/repository.py`, `trade_closer.py` |
| report | 期間損益・勝率・最大 DD・判断内訳 + 「実弾期待値」の概算 | `report/metrics.py`, `live_estimate.py` |
| domain | Decimal ラッパー（Money / Price / Quantity）、Result 型、Clock、frozen なモデル | `domain/` |

### データの流れ（1 サイクル = `trader run-cycle`、市場時間内に cron で 15 分おき）

```
[手動] ツイートアーカイブ JSON → data/sources/serenity/
            │ trader ingest（pydantic 検証、不正レコードがあれば全件拒否）
            ▼
       ledger.mentions（銘柄 × 言及の正規化テーブル）

[cron] trader run-cycle
  1. 起動検証: モード・API キー・ルール lock（SHA-256）・halted 状態
  2. 保有ポジション評価: 現在値取得 → 高値更新 → 損切り / 部分利確 / トレーリング / 保有期限 → 売り decision
  3. 口座評価額を記録 → 日次 / 週次 / ドローダウンの損失上限チェック → 超えていればキルスイッチ
  4. 新規候補: 直近 14 日に言及された銘柄（上位 20）→ 株価付与 → LLM に一括で問い合わせ
     → buy 提案だけルールエンジン（entry_checks）を通す → passed / rejected として記録
  5. passed な decision → 承認（paper は system 自動承認、live は人間の承認レコード必須）
  6. 「DB に記録してから」ブローカーへ送信 → 約定ポーリング → fills / positions / trades 更新
  7. cycles テーブルにサイクル結果を記録

[人間] trader report / trader status で成績と状態を確認
```

### 安全装置の多層構造（スライドの図にしやすいポイント）

```
LLM の提案 ──→ ルールエンジン ──→ 承認 ──→ 記録 ──→ 発注
   │              │              │         │        │
  sell を       上限 / 保有数 /  live は    DB 書込  唯一の
  出せない      損失上限 /      人間承認   失敗なら  発注経路
  スキーマ      市場時間        必須       送信せず  (静的チェック)
```

## 3. 技術スタック

| 開発プロセス | Claude Code のカスタムエージェント + hooks（後述） | intent → spec → plan → 自律 build/test/review ループ |

規模感: ソース約 7,000 行、テストファイル 45 本、テスト関数約 440 本、コミット約 70。

## 4. 売買ロジックのざっくりした考え方

### 基本思想: 「買うのは AI、売るのはルール」

- **情報源**: AI インフラ関連の小型〜中型米株を扱う SNS 発信者の言及データ。発信者の予想は的中率が独立検証されておらず、投稿後にフォロワーが殺到して高値になりやすい。そのため「いつ売るか」が利益を決めるという前提に立つ
- **買い（LLM）**: 直近 14 日の言及履歴（初出・言及回数の増減・抜粋）と直近 20 日の日足・平均出来高を渡し、`buy / hold / skip` と根拠・確信度を JSON で返させる。LLM は候補リスト外の銘柄を提案できず、`sell` も出せない
- **買い前チェック（ルール）**: 対象外銘柄でない / 同時保有数未満 / 1 銘柄上限以下 / 未保有 / 損失上限未到達 / 市場時間内 / 最低株価と最低出来高（流動性）。整数株のみ
- **売り（ルール、LLM を待たない）**: 損切り / 部分利確（到達で半分売却）/ 残り半分にトレーリングストップ / 保有期間上限で強制クローズ
- **損失上限（キルスイッチ）**: 日次・週次の損失、口座全体のドローダウンのいずれかで、未約定注文を全キャンセルし新規発注を停止。人間が `resume` するまで再開しない

### ルールの設計方針

- 金額は全て **運用資金に対する割合** で定義し、絶対額は起動時に導出する。資金額を変えても作戦（比率）は変えなくてよい
- 比率の根拠を YAML のコメントに書く（例: 対象銘柄は 1 日 15〜25% 動くので、一般的な -8% の損切りはノイズで狩られる → 損切りは 1 日の揺れの上限に近い水準に置く。1 ポジションの最大損失 = 1 銘柄上限 × 損切り幅 = 資金の数 %）
- ルール変更は人間の承認が必須。ファイルの SHA-256 を lock に記録し、不一致なら起動しない。LLM モジュールはルールファイルへのファイルアクセス自体を持たない

### 段階的な導入

1. paper（模擬口座）で数週間運用し、成績と挙動を確認 ← **今ここ**
2. 少額の実弾。売買ごとに人間が承認（承認レコードの仕組みはすでに実装済み）
3. 条件付き自動 + 人間確認のハイブリッド
4. 自動の範囲を拡大

## 5. 技術的に工夫した点・面白いポイント

### (a) LLM を「信用しない」設計
- LLM の出力は発注シグナルではなく **提案**。必ずルールエンジンを通る
- 出力スキーマに「ルールを変えるフィールド」が存在しない。`action` の enum に `sell` がない。API の構造化出力で JSON Schema を強制し、さらに pydantic で再検証
- 「ルールエンジンを迂回する発注 API が存在しない」ことをテストで静的に検証（`Broker.submit_market_order` を呼べる場所がただ 1 つであることを AST でチェック）
- プロンプトにはルールを「読み取り専用のテキスト要約」として渡し、ファイル名やパスは一切入れない

### (b) 「記録してから発注」（Record-before-submit）
- 判断 → 承認 → 注文の 3 レコードを 1 トランザクションで DB に書き、**コミット成功後にだけ** ブローカーへ送信。DB 書き込みが失敗したら発注しない（記録できない売買は実行しない）
- 発注 POST はリトライしない（二重発注防止）。`client_order_id` で冪等性。GET だけ指数バックオフで再試行

### (c) 金額に float を使わない
- `Money`（セント単位に量子化）/ `Price`（小数 4 桁）/ `Quantity` の frozen dataclass で Decimal をラップ
- domain / broker / ledger / rules 配下で `float` の型注釈・`float()` 呼び出しを AST 走査して禁止するスクリプトを受入基準に組み込み

### (d) paper と live を同じコードパスで、しかし混ざらないように
- `TRADER_MODE` 省略時は paper。live は「モード + live キー + 明示的な確認変数」の 3 つが揃わないと起動拒否。テスト環境では条件が揃っても live を拒否
- paper の Settings クラスは live の環境変数を**読まない**（フィールド自体が存在しない）。読み取り用キーと取引用キーを分け、trade キーが無ければ `Broker` を構築できない型設計

### (e) 全部 Result 型 + 全部 frozen
- 失敗しうる処理は `Ok[T] | Err[E]` を返す。例外は外部 SDK の境界で捕捉して `Err` に変換。CLI 層で人間が読めるメッセージに変換し、スタックトレース・パス・キーは出さない
- ドメインモデルは全て frozen。イミュータブルであることをテストで一括検証

### (f) 開発プロセス自体をハーネス化（Claude Code）
- 人間が関わるのは **intent / spec / plan の承認** と **デプロイ後の確認** だけ。その間は builder（実装）→ tester（TDD）→ reviewer（3 パスレビュー）の AI エージェントが自律ループ
- spec の受入基準を `- [ ] AC-n: ... / verify: <shell command>` の厳密形式で書き、**Stop hook** が全 verify を実行して、通るまでセッション終了をブロック（上限 8 回で halted）
- reviewer の REJECT は builder に差し戻し（上限 5 回）。builder はテストを書き換えて通すことを禁止
- production デプロイ相当のコマンドは PreToolUse hook が `RELEASE_APPROVAL` 無しではブロック
- 結果: 33 個の受入基準すべてに自動 verify が付き、レビュー指摘（注文数量の切り捨て誤差、承認期限のタイムゾーン比較、部分約定の価格計算など）が RED テスト → 修正の形で履歴に残っている

### (g) 「実弾期待値」を paper 成績に並べる
- paper の損益から、想定スリッページ・手数料・為替コストを差し引いた概算を report に出す。係数はルールファイルに置き、live 業者が決まったら差し替える

## 6. 苦労した点・ハマったところ

### 実データ・実 API に当てて初めて分かったこと（デプロイ後の fix の履歴から）

1. **実データのフィールド名が想定と違った**
   アーカイブ JSON は `created_at` ではなく `createdAtISO` / `createdAt`（Twitter 形式）/ `sourceUrl` を持っていて、全件がスキーマ違反扱いになった。pydantic の `AliasChoices` で複数の綴りと Twitter 形式の日付を受け付けるようにした。「fail fast」が効いて黙って壊れなかったのは良かった
2. **候補の絞り込みがアルファベット順だった**
   直近 14 日に言及のある銘柄が想定よりずっと多く、上限 20 への絞り込みがティッカー順だったため、言及の多い銘柄が落ちていた。言及回数の降順に変更
3. **cron の PATH 問題**
   cron の PATH は `/usr/bin:/bin` だけなので `uv` が見つからず、サイクルが一度も走っていなかった。Homebrew 等の既知の場所を探し、見つからなければ明示的なメッセージで失敗するように
4. **LLM API のパラメータ仕様変更**
   `temperature` を送っていたら新しいモデルで HTTP 400。全候補が「LLM 呼び出し失敗」として記録され続けていた。サンプリングパラメータを外し、エラーメッセージに HTTP ステータスと API のメッセージ（キーや生ボディは含めない）を入れて次回から診断できるようにした
5. **応答の最初のブロックが text とは限らない**
   思考ブロックが先頭に来る設定だと `content[0]` が text ではない。「最初の text ブロック」を取るように変更
6. **JSON が途中で切れていた**
   20 銘柄分の根拠を含む JSON に対して `max_tokens` が小さく、途中で切れて「JSON として不正」になっていた。上限を引き上げ、`stop_reason=max_tokens` を「不正 JSON」ではなく明示的なエラーとして扱い、構造化出力で JSON 形式を API 側に保証させた
7. **寄り付き直後に候補が全滅**
   日足 API の `start` を省略すると「当日 0 時」が既定になり、09:30 の開場直後は足が 1 本も返らない（= 全候補が落ちる）。日中も当日の部分足 1 本だけで 20 日平均出来高を評価していた。過去 45 日を明示して取得するように
8. **無駄な LLM 呼び出し**
   保有枠が埋まっているときも毎サイクル 20 銘柄の株価取得 + LLM 呼び出しをしていた（1 日 26 回）。枠が埋まっていれば候補評価をスキップ

### 設計・レビューで詰まったところ

- **注文数量の切り捨て誤差**: セント単位に量子化した金額を小数 4 桁の価格で割ると 1 株少なく出る。半セント補正してから切り捨て
- **承認期限の比較**: ISO 文字列のまま比較していたため、UTC 以外のオフセットで「期限内」と誤判定しうる。保存時に UTC に正規化し、絶対時刻として比較
- **部分約定の価格**: ブローカーの「累計平均価格」をそのまま記録すると、追加分の約定価格がずれて平均取得単価が狂う。累計金額の差分から今回分の価格を計算
- **保有銘柄の一部が値取得不能なとき**: 当初は「サイクルを丸ごと中断」したが、それだと別の銘柄の損切りまで止まってしまう。「評価額の記録と新規買いは止めるが、既に判定済みの売りは実行する」に修正
- **同一バッチ内の重複**: LLM が 1 回の応答で複数の buy を返すとき、同時保有数のチェックがサイクル開始時のスナップショットにしか効いていなかった。バッチ内で passed が増えるたびに保有集合を更新
- **デバッグ用スクリプトの必要性**: 「なぜ decision が 0 件なのか」を DB に書かずに説明するスクリプト（言及数・候補・銘柄別の市場データエラー・任意で LLM 提案を出す）を作って初めて上記の原因が分かった

### 教訓としてまとめるなら

- ユニットテスト + Fake で全 AC を通しても、**実データの形・実 API の既定値・cron の環境**は本番に当てるまで分からない
- だからこそ「黙って壊れない」設計（境界で fail fast、エラー理由を記録に残す、Result 型）が効いた。壊れていることは即座に分かり、理由も追えた

## 7. 今後やりたいこと

- **paper 運用の継続と計測**: 損切り発火回数、ドローダウン推移、「1 株が上限を超えて見送った回数」を見てルールの比率を調整する
- **少額実弾への移行（段階 2）**: 承認フローの土台は実装済み。移行条件の案は「paper 3 週間以上 + 閉じたトレード 10 件以上 + 実弾期待値がプラス + 最大 DD が週次上限未満 + キルスイッチの誤作動なし」
- **実口座の証券会社を決め直す**: 国内業者（円入金・特定口座）が本命。`Broker` インターフェースの実装を 1 つ追加するだけで差し替えられる設計にしてある。海外業者は海外送金コストと確定申告がネック
- **ハイブリッド自動化（段階 3）**: 判断に `origin` / `confidence` / `rule_check` を残しているので、条件別の成績を集計して「どの条件なら自動、どれは人間に聞く」を決める
- **情報源の追加**: `SourceAdapter` を追加するだけで別の発信者・データ源を取り込める。追加基準（構造化アーカイブがある / 監査済み / 実績期間）は運用で決める
- **集約データの自動更新**: 現在は手動コピー + 冪等な再取り込み。自前取得はスコープ外のまま
- **手数料の実額取得**: Alpaca の約定情報に手数料が含まれないため現状はゼロで記録。activities API との連携は live 移行時に
- **発信者の方法論をプロンプトへ**: 今は言及履歴と株価だけを渡している。方法論・銘柄別テーゼの要約を人間がレビューしてプロンプトに入れる運用を検討
